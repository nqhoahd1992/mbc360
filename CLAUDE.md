## Working agreements (read before changing any business rule)

**Do not speculate.** This system encodes a lot of externally-owned rules, so the default is: if the workbook or the SME's own words do not say it, do not decide it silently. Speculate only where the signal is overwhelming — and then it goes on the question list, kept if the SME confirms it and fixed if not. The user's own words (2026-08-09): *"suy đoán chỉ xảy ra khi nó có dấu hiệu quá rõ ràng, và suy đoán sẽ được liệt kê vào câu hỏi cho SME để họ confirm. SME confirm đúng giữ nguyên, sai thì sửa."* The user approving something in conversation authorises **building** it; it does not make the underlying interpretation a confirmed rule.

**Every speculation gets an ID and a tag.** Add it to the newest round in `docs/rules/F1_Per_Gate_Open_Questions.md`, give it a stable ID (the form is `Rn-Qm`, e.g. `R5-Q7`) and a line naming the file/function to change if the answer differs, then tag the decision site — in code comments **and** docs — with `[ASSUMPTION: R5-Qm]`. `npm run verify:readiness` fails if a tag points at no question, or a question is untagged, so this does not depend on anyone remembering. The sendable, jargon-free version of each round lives in `docs/rounds/`; that folder is evidence and is never edited after sending.

**The two speculations that have actually cost us**, both worth recognising before repeating:
- *One that looks mechanical.* Mapping an SME's prose onto specific dropdown options, or picking one of several plausible signals, feels like plumbing but is interpretation. `sg01-source` and `sg01-owner` were each wired to a plausible-looking nearby field and both had to be reverted.
- *One that quietly narrows a rule.* Dropping the half of a condition you cannot evaluate (e.g. "a Change Control record has been opened **or should be opened**") and recording only the half you implemented makes the rule look fully covered.

**Run `npm run verify:scaffold` after adding a checklist section, a requirement row, a Key Gate Check row or a fixed register's rows.** Those rows are materialised ONCE, at project creation — adding a section to config gives it to future projects only, so every existing project shows that table empty and any readiness check reading it can never be satisfied there. Nothing fails and nothing logs; it just looks like a feature nobody built. It has happened four times: 2026-08-10/11 (the two gate-01 checklists, then Phase 1's 16-row Project Requirements & Exclusions) and again on 2026-08-12, when the two Key Gate Check rows added for SME B2 and C2 on 2026-08-09 turned out never to have reached the existing project — leaving Gates 01 and 04 blocked by a Mandatory item with **no row on screen to tick**. Every one was found by a person, not by tooling. The third case also exposed a hole in this very script: it covered checklist sections, requirement sections and fixed registers but **not gate checks**, so it reported clean while two gates were unsatisfiable; gate checks are now compared by **identity**, not count, since a renamed check leaves the count equal while breaking the item that reads it. The fix is always a migration that backfills existing projects with rows **generated from the same config a new project reads** — `20260810041500`, `20260811071500` and `20260812043000` are the templates.

**Run `npm run verify:readiness` after touching gate-readiness config.** It catches the three failure modes that are invisible at runtime — a mistyped reference that makes a check unsatisfiable forever, a check vacuously satisfied on an empty register, and a `mode: 'fixed'` register whose seeded values decide the check (that last one shipped as the Gate 7 bug).

**Never kill the dev server.** The user runs their own `npm run dev`; `npm run dev` (its `predev` runs `kill-port`) and any port-based kill both tear theirs down.

## Commands

All from the repo root:

```
npm run dev       # build shared once, then run shared (tsc -w) + api (:3000) + web (Vite HMR) concurrently
npm run build     # build shared -> api -> web (order matters: apps compile against shared's dist)
npm run lint      # oxlint across the whole repo
docker compose -f docker-compose.dev.yml up -d   # dev Postgres (apps are NOT containerized in dev)
npm run db:migrate -w @mbc360/api   # prisma migrate dev (needs dev Postgres up + apps/api/.env, see .env.example)
npm run db:seed -w @mbc360/api      # idempotent seeder: rule config + demo project scaffolded from shared config
npm run db:setup                    # all three of the above in order — run this after a fresh clone or a wiped/new Postgres volume
npm run db:reset                    # ./reset-dev-data.sh — wipe the dev DB and re-seed the standard dataset (keeps the Cosmetri tokens)
npm run verify:totp                 # RFC 6238 vectors against the hand-written TOTP module (see the sign-off note below)
```

**`./reset-dev-data.sh` (2026-07-26) is the one command for "give me clean data again".** It preserves ONLY the `cosmetri_connection` token pair (dumped before the wipe, restored after — that row can only be recreated by pasting tokens obtained out-of-band from the real Cosmetri account, everything else is generated from config), then runs `prisma migrate reset` + the seeder, then prints a row-count table and **fails if the database came back empty**. Flags: `--yes` (no prompt), `--keep-users` (also preserve real `@`-domain SSO users, restored by role KEY since role ids are regenerated). It refuses to run unless `DATABASE_URL` points at localhost, so it cannot be aimed at production. Three gotchas it exists to encode: **(1) Prisma 7's `migrate reset` does NOT run the seed** despite `migrations.seed` in `prisma.config.ts` — it reports success and leaves an empty database, so the seed must be a separate step (this is why `db:setup` also calls `db:seed` explicitly); (2) the backup holds real tokens, so it is deleted when redundant and kept (loudly) only when a restore failed; (3) Prisma blocks an AI agent from running `migrate reset` at all — a human running the script is unaffected.

**Fresh/reset dev Postgres → `npm run db:setup` before `npm run dev`.** A new (or volume-wiped) dev Postgres container starts with an empty `public` schema — no `users` table, no seeded roles. `npm run dev` itself never runs migrations (deliberately — migrations must be a conscious step), so starting the API against a schema-less DB surfaces as `PrismaClientKnownRequestError P2021: The table "public.users" does not exist` the moment anyone hits an endpoint that touches Prisma (e.g. the OIDC callback in `AuthService.upsertSsoUser`). Always run `npm run db:setup` (or the 3 commands above in order) once after: first clone on a new machine, `docker compose down -v` / any Postgres volume reset, or pulling a branch with new Prisma migrations.

Per-workspace: `npm run <script> -w @mbc360/web|@mbc360/api|@mbc360/shared`. If TypeScript can't resolve `@mbc360/shared/*`, build the shared package first (`npm run build -w @mbc360/shared`). The Vite dev server proxies `/api` → `localhost:3000` (same-origin, mirroring production nginx routing) — the frontend must always call relative `/api/...` URLs.

**`apps/web/vite.config.ts` aliases every `@mbc360/shared/*` import straight to its TypeScript SOURCE in dev (2026-07-26, replacing the old prebundle approach below — fixes a long-standing "edit shared, must restart the dev server to see it" complaint).** `resolve.alias`, active only when `command === 'serve'`, maps `@mbc360/shared/types` / `@mbc360/shared/config/*` / `@mbc360/shared/utils/*` to `packages/shared/src/.../*.ts` — real ESM, so Vite transforms it on the fly and hot-reloads it exactly like `apps/web/src` code. `vite build` (production) is untouched: with no `alias` entries added, it still resolves through `package.json`'s `exports` map to the compiled `dist`, same as always; `apps/api` is unaffected either way (it never goes through Vite). Extend the alias's regex-based entries automatically cover any new `@mbc360/shared/config/*` or `/utils/*` subpath — no per-file list to maintain any more, unlike the old approach.

~~`apps/web/vite.config.ts` used to force-prebundle every `@mbc360/shared/*` subpath through esbuild (`optimizeDeps.include`+`force: true`), needed so the dev server's native-ESM import handling could read named exports off `shared`'s CJS build.~~ That prebundle only ran at dev-server **start** and never re-checked afterwards (Vite treats a "dependency" prebundle as immutable for the rest of the session by design) — so editing `packages/shared` always required a full restart to be seen, even though `packages/shared`'s own `tsc --watch` (part of `npm run dev`) had already recompiled `dist` within a second. ## Architecture

### Phase-Gate domain model

The business process is **4 Phases containing 12 Gates (SG01–SG12)**, plus cross-cutting Change Control. Phase/Gate metadata (owners, purpose, key outputs) lives in `packages/shared/src/config/gates.ts` (`PHASES`, `GATES`, `EIGHT_ANGLES`, status/decision enum arrays). Gate progression rules live in `packages/shared/src/utils/gateProgress.ts` and implement the **confirmed business rules** in `docs/rules/Business_Rules_Confirmation_{EN,VN}.md` (rule IDs like B1/B3/C1 below refer to that document — read it before changing any rule):

- A gate is **passed** (B1) only when `status === 'Complete'`, a positive `decision` (`Proceed` / `Proceed with Conditions`) is recorded, AND `gateBlockers()` is empty — open next actions block a plain `Proceed` (allowed to stay open only under `Proceed with Conditions`, B2), and the Skincare-for-Two safety screen hard-blocks SG07 when the Gate 02 target users include Pregnancy/Breastfeeding/Postpartum (C1). A `Gap` status prevents a normal `Proceed` (enforced in both `GateFlowTable` and the store's `setGate`). **2026-07-22:** `gateBlockers()` now composes from `hardGateBlockers()` (Critical next actions, Skincare for Two, F1/C7 Mandatory evidence — none of these are cleared by Proceed with Conditions either) plus the softer open-non-critical-next-action blocker (the one thing Proceed with Conditions is designed to clear). **2026-07-23 (revised again, same day):** disabling the "Proceed"/"Proceed with Conditions" *options themselves* in the dropdown (the 2026-07-22 fix above) hid *why* from the user — both are now left selectable regardless of blockers; instead the Save button disables (`SaveBar`'s `disabled`/`disabledReason`, same pattern as the BOM duplicate-line guard) whenever the currently-drafted decision would be rejected, backed by a red banner and a per-gate, always-visible "What's blocking this gate" list rendered as its own **full-width row below each gate** (antd Table `expandable`, `showExpandColumn: false`, fully controlled — not user-toggleable — so long blocker lists no longer cram into the narrow "Gate decision" column). `gateBlockers()` gained an optional `decisionOverride` param so this live guidance (and the Save-guard) can be evaluated against the *draft* decision, not just the last-committed one. Separately, the store guard (`setGate`/`setGatesBulk`) previously only enforced `gateBlockers()`/`hardGateBlockers()` for a `Proceed` decision — `Proceed with Conditions` had **no store-side check at all**, only the (now-removed) UI dropdown-disable — so a direct store/API call could record Proceed with Conditions despite unmet F1/C7 Mandatory evidence. Both decisions are now guarded identically at the store layer, independent of what the UI does.
- A **phase** is complete (B3) only per `phaseCompletionChecklist`: all gates passed + key gate checks done (or N/A **with justification** in notes) + all 8 angles covered (or justified N/A) + next actions closed (unless Proceed with Conditions) + **pre-work reviewed/accepted (F13, added 2026-07-22 — see below)** + all three sign-off roles signed. `SignOffBlock` stays locked until `canSignOff` is true.
- **Gate-level evidence edit lock (2026-07-23, user-requested):** once a gate has genuinely PASSED (`isGatePassed` — Complete + Proceed/PwC + no blockers), the evidence tied to it becomes READ-ONLY across the whole app; correcting it requires Backtrack (which un-passes the gate, B4). `isGateRefLocked(project, gateRef)` in `gateProgress.ts` is the predicate — `gateRef` is a config `gate` string ('04', '04/07', '05/07/10', 'ALL', undefined); a page/register used at SEVERAL gates only locks once EVERY one has passed (e.g. Ingredient Substitution Evidence `04/07` stays editable through Gate 07), and 'ALL'/undefined (cross-cutting evidence) never lock. Because it keys off `isGatePassed` (not just a Proceed stamp), a gate that's Complete/Proceed but still has open F1/C7 mandatory evidence is NOT locked yet — so the very evidence a gate needs to pass stays editable until it actually passes. Enforced at BOTH layers (defense in depth, matching the guard-parity principle): UI renders read-only (`readOnly` on `DynamicTable`/`SupplierRmEvidenceTable` → static cells + lock banner + no Add/Delete/Save; per-section `readOnly`/`isRowLocked` on `ChecklistSection`/`RequirementTable`/`GateChecksTable` in `PhasePage`; per-section banners + disabled Save/Add/inputs in `BomCosting` gate 05/06 and `FormulationSafety` gate 07/10), AND the store setters refuse the write (`setChecklistSection`/`setRequirementSection` [per-row merge] / `setGateChecksBulk` [per-row skip] / `setRegisterRowsBulk` / `setBom` / `setCosting` / `setPackagingBomBulk`). `GateFlowTable`'s own row-edit lock (`isGateUnlocked`, current gate only) is separate and unchanged. Verified live: Phase 1 (gates 1–3 passed) renders every checklist/requirement/gate-check section read-only; Ingredient Substitution (04/07) and Formula BOM (gate 05 in progress) stay editable.
- **NPD Front-End Roadmap (2026-07-24, from `docs/reference/MBc360 Master Product Development System File v2.xlsx` — expert-authored, treated as confirmed spec with the same authority as the original workbook, no separate SME round needed):** adds a mandatory 4-step scientific front-end that must be signed off before Formula BOM lock — (1) Needs & Scientific Basis (sign-off gate SG02), (2) Competitor Landscape (SG03), (3) Target Product Profile & Backbone Technology ("complete before formula lock — Gate 5"), (4) Evidence Plan (before Gate 5) then Detailed Test Protocol (Gate 8). Modeled entirely as `RegisterConfig` entries (~25 new registers in `registers.ts`, no new `ProjectData` fields) under a new nav group `dept-npd-frontend` — including the two "Name/Date, 3 fixed roles" sign-off blocks (`needsSignOff`, `targetProductSignOff`), reusing `DynamicTable`'s existing gate-lock support rather than a bespoke sign-off component. One new `ReadinessCheck` kind, `registerRowsComplete` (`gateReadiness.ts`/`gateProgress.ts`) — a multi-column generalization of `registerColumnFilled`, satisfied only when every row of a register has every listed column filled (deliberately NOT vacuously true on an empty register, unlike `registerColumnFilled`, since it backs sign-off-style hard blocks). 10 new `GATE_READINESS` rows wired at SG02 (2 Mandatory), SG03 (1 Mandatory content check + 1 Supporting visibility nudge), SG05 (5 Mandatory — this is the actual "Formula BOM held pending Steps 1-3" hard block, verified live end-to-end: empty dossiers block Gate 05's Proceed decision with all 5 items listed in "What's blocking Gate 05"; filling all 5 clears them), and SG08 (1 Mandatory). All reuse the existing `gateBlockers()`/`hardGateBlockers()`/`setGate` pipeline with zero changes there — same "guard parity for free" property the gate-evidence-lock feature established. **Bug caught during live verification, fixed same day:** two new items (`sg03-npd-target-product-progress`, `sg05-npd-target-product-content`) originally used `registerHasRows` against `targetProductProfile`, a `mode:'fixed'` register whose 7 attribute-label rows are seeded at project creation regardless of user input — `registerHasRows` (rows.length > 0) was therefore vacuously always true and could never actually block. Fixed to `registerColumnFilled(targetProductProfile, 'target')`, which checks a real answer column that starts blank. 4 new bespoke pages (`NeedsScientificBasis`, `CompetitorLandscape`, `TargetProductTech`, `EvidenceClaimSupport`), each following `FormulationSafety.tsx`'s template exactly (no local draft state, stacked `DynamicTable`s); the other new sheets (Ingredient Monograph, Evidence & Search Rules, Carrier/Emollient Review, the Roadmap sheet's own reference tables) are plain nav-group register entries with no bespoke page, per the existing `Released Label Control` precedent. `claimEvidenceTraceability`'s "no claim without a Supported Claim ID" rule is Supporting-tier only (non-blocking) — hard-enforcing it would mean touching the existing Published Info / SKU_Claims_PIF (C6/F11) workflow, deliberately out of scope here. Persist bumped v11→v12 (re-seeds) — required, not cosmetic, since `mode:'fixed'` registers never materialize their rows for an already-persisted project without it, and the new SG02/03/05/08 Mandatory checks read live `project.registers` data that an un-reseeded project would be missing entirely.
- Gates unlock **strictly in order** — `isGateUnlocked` / `currentGateIndex` compute the single gate currently open for work. **Fixed 2026-07-22:** `isGateUnlocked` used to allow editing any gate at or before the current index (`<=`), contradicting its own doc comment ("the single gate currently open for work") — an already-PASSED gate's Phase Gate Flow row was silently editable with no audit trail, defeating B4's "no silent corrections" intent. Now strictly `===` current; `GateFlowTable`'s `locked` flag (and the store's `setGate`/`setGatesBulk` guard) matches — correcting a passed gate now requires Backtrack.
- `backtrackGate` (B4, "no silent corrections") reopens a gate range and invalidates affected approvals but **never deletes**: pre-backtrack gate records and sign-offs are snapshotted into `ProjectData.backtrackEvents` (shown on Project Overview, and per-gate via the "History" column on `GateFlowTable` — 2026-07-22). Who/why/when lives **only** on that immutable event — it's deliberately never also written into the mutable `notes` field (the pre-2026-07-22 code did this via `appendNote`; removed, since a free-text field can be overwritten, silently losing the audit trail). The Backtrack modal's "Initiated by" is now the real signed-in identity (`useSession()`), read-only, not free text; all 3 fields (target gate/initiator/reason) are mandatory to confirm; Gate 1 has no "Backtrack" option (nothing earlier to reopen). **2026-07-22, separately:** every ordinary Phase Gate Flow field edit (not just backtrack) is now diffed and logged to a new append-only `ProjectData.gateChangeLog` (`GateChangeLogEntry`/`GateFieldChange`, `setGate`/`setGatesBulk` accept a `changedBy` and only log fields that actually changed) — surfaced next to `backtrackEvents` in the same "History" popup/Project-Overview card. **Fixed 2026-07-23 (user-reported):** the gate you backtrack *from* (`fromGateId`) used to be excluded from the reset range and instead just had its `decision` stamped `'Backtrack'` as a permanent marker — so it kept showing "Backtrack" selected in the Gate Flow table forever instead of reopening like the rest of the range, and (since it's the range's own upper bound) silently skipped invalidating a phase whose *closing* gate is `fromGateId` itself. `fromGateId` is now included in the reset range (`status: 'Not Started'`, `decision: undefined`) exactly like every other gate in it, and `reopenedGateIds` on the `BacktrackEvent` includes it too. **Fixed 2026-07-23, separately (user-requested):** sign-off invalidation used to clear only the "Approved by" role, and only for a phase whose *closing* gate fell inside the range — broadened to clear **all three roles** (Prepared/Reviewed/Approved) for **every** phase with at least one gate anywhere in the range, since a phase earlier in the range (not the one containing `fromGateId`) can very well already be fully signed off (e.g. backtracking from Gate 8 to Gate 3 also resets Gates 4–6, and Phase 2 — already complete and signed since the project had reached Gate 8 — must lose its sign-offs too, not just its final approval). `createFormulaVersion` (A2) reuses the backtrack pattern for Major formula changes: bumps `formulaVersion`, reopens SG04–SG09, invalidates Phase 2–3 approvals (same all-three-roles / any-affected-phase fix applied there too, 2026-07-23) and appends to the Formulation Change Register. It also snapshots the outgoing Formula BOM into the new `FormulaVersionRecord.previousBomSnapshot` (2026-07-17) — `BomCosting.tsx`'s "Formula version history" card uses this (plus the live `bom`) to view/diff any two versions via `packages/shared/src/utils/formulaDiff.ts` + `FormulaVersionCompareModal`; history entries created before this existed have no snapshot and show as "not available" rather than a fabricated diff.
- Gates 10–12 are additionally tracked **per market** in `ProjectData.marketTracks` (A1); a market's launch approval is hard-blocked until its PIF status is Approved (C5) — enforced in `setMarketTracksBulk` and `MarketTrackingCard`.
- The Study/Human Trial approval trail (C2) is a dedicated 3-role workflow (`ProjectData.studyApprovals`, `StudyApprovalCard` on the Study Protocol register); the Independent Reviewer must not share the Study Author's department (enforced in `setStudyApprovalsBulk` and the UI).

When changing gate/phase logic, `gateProgress.ts` is the single place that encodes these rules — pages/components only call its exported helpers (`gateState`, `phaseProgress`, `gateBlockers`, `phaseCompletionChecklist`, etc.), they don't re-derive pass/lock state themselves.

### RBAC simulation & integrations

- **RBAC (A4, demo simulation):** the header's "View as" selector (`viewRole` in the store) stands in for the logged-in user's role. Gate decisions, the phase "Approved by" row and market-track approvals are restricted by role; evidence fields stay open to contributors. **2026-07-23:** the frontend permission checks moved from the keyword-match token functions in `@mbc360/shared/config/roles` to a **live DB permission grid** — `apps/web/src/utils/permissions.ts` (`canDecideGate`/`canApprovePhase`/`canEditMarketTrack`) reads the `role_permissions` grid loaded into the store (`permissionGrid`, via `GET /api/rbac/permissions-grid`, not persisted — always fetched fresh on startup in `App.tsx`). The shared token functions remain **only** as the seed default `seedRbac()` uses to populate that grid initially. The grid is editable by an admin in the **Role Editor** (`apps/web/src/components/RoleCapabilityEditor.tsx`, in the Users & Roles page — role dropdown + grouped capability checkboxes (Gate decisions / Phase approvals / Market tracking) + a single "Save Changes" button, modeled loosely on the WordPress User Role Editor): `PUT /api/rbac/roles/:key/permissions` (admin-only, audited, transactional) saves a role's granted capabilities, then the store grid is reloaded so "View as" reflects the change live. A capability id is `${resource}|${action}` (e.g. `gate:SG07|decide`, `phase:3|approve`, `market-track|approve`). System Administrator (`admin`) is unrestricted (short-circuits in both `PermissionsService.isAdmin` and the frontend helper) and its grid is not editable. The **initial** grants are still F6's keyword-match derivation (not the SME-confirmed role×gate/phase matrix, which is F6's still-open remainder) — but now they're an editable starting point, not hardcoded. `apps/web/src/utils/roles.ts` now only re-exports the role list + `roleLabel` (the permission-check functions moved out).
- **Integrations (A3):** `/integrations` page + `apps/web/src/integrations/cosmetri.ts`, a thin client that calls MBc360's own backend proxy (`apps/api/src/cosmetri/cosmetri-data.service.ts`) for formulas, raw materials (`supplier_name`, `status_label`) and compliance (INCI/CAS) — real Cosmetri data end-to-end since 2026-07-17, no more frontend mock (see `docs/reference/swagger-init.json` for the underlying Cosmetri shapes). Cosmetri is strictly read-only; the Formula BOM can be imported from it (`CosmetriImportModal`, gated on `useCosmetriStatus().connected`). `/formula/list`+`/formula/details` only return IDs/reference/quality-status (no product title or formula version), so the picker list shows those two blank until a formula is actually selected — a real Cosmetri API limitation, not a bug. Matching a composition row's INCI/CAS is a best-effort join by raw-material trade name against `/compliance/{id}`'s `INCI_source_raw_materials[].raw_title`, since that endpoint carries no raw-material ID — **so on a `fromCosmetri` BOM line, Ingredient/INCI and CAS no. stay user-editable (2026-07-22 fix)** rather than locked read-only like Supplier/% w/w (which *are* direct, reliable Cosmetri fields) — the join can come back blank or wrong and there was previously no way to correct it. Data the API doesn't provide (supplier details beyond the name, SDS/CoA/TDS links) is entered manually. New raw materials go through the Power Apps "Create new raw material" change request (URL configurable on the Integrations page — currently a placeholder). ### Editable tables: local draft + explicit Save, never per-keystroke store writes

Every inline-editable table (all 6 reusable blocks above, `DynamicTable`, `NextActionsCard`, `StudyApprovalCard`, `MarketTrackingCard`, the BOM/Packaging/Costing sections of `BomCosting.tsx`, `EvidenceSummary`, the editable columns of `PostMarketCapa`/`ChangeControl`, and the Graph settings on `IntegrationsPage`) uses `apps/web/src/hooks/useDraft.ts` + `apps/web/src/components/SaveBar.tsx` (decided 2026-07-17 — see the `draft-save-pattern` memory). Typing/selecting only updates local component state (instant, no lag); a "Save"/"Discard" bar appears while that draft differs from the committed store data, and Save commits everything in one write. This exists because a per-keystroke store write re-runs `JSON.stringify` + `localStorage.setItem` on the WHOLE persisted store (via `persist` middleware), which visibly lags as project data grows.

**When adding a new editable table, use this pattern — don't wire a new input straight to a per-row store setter.** The store only exposes **bulk** setters for table-shaped data (`setChecklistSection`, `setRequirementSection`, `setGateChecksBulk`, `setAnglesBulk`, `setSignOffsBulk`, `setPackagingBomBulk`, `setRegisterRowsBulk`, `setEvidenceItemsBulk`, `setCapaBulk`, `setChangesBulk`, `setNextActionsBulk`, `setMarketTracksBulk`, `setStudyApprovalsBulk`, `setGatesBulk`, plus `setBom`/`setCosting`) — the old per-row setters (`setChecklistItem`, `setRegisterRow`, `setBomLine`, ...) were deleted once nothing called them. Row add/remove also happens in the local draft (not by calling the store directly), so structural edits save atomically with the rest of the table. Modal-gated "Add new record" flows (CAPA, Change Control, Cosmetri import, formula version) are unaffected — they already commit only on an explicit submit button.

**`GateFlowTable` fixed to actually follow this pattern (2026-07-22)** — despite being listed among "the 6 reusable blocks" since this rule was written, it had never been converted: every field (Stage status, Gate decision, Owner, Due date, Evidence link, Notes) wrote straight to the store per keystroke via `setGate`, which was the exact per-keystroke-lag problem this section exists to prevent. Converted to `useDraft` + the new bulk `setGatesBulk` (which preserves `setGate`'s B1/F9 decision guards, scoped only to the `decision` field so an invalid decision never discards a row's other valid edits). Two flows still commit immediately by design, matching the "modal-gated flows are exempt" rule above: the F9 "acknowledge open change control" confirm (which also mirrors its result into the draft so a later Save can't clobber it) and Backtrack (which discards any pending draft on this table afterward, since it resets a whole gate range client-side replication would be error-prone to mirror).

**Non-obvious pitfall (the second half of the same family, 2026-08-11):** a **zustand selector must never build a new object**. `useAppStore((s) => … ?? [])` allocates a fresh array on every call, so `useSyncExternalStore` — which compares snapshots by reference — sees a change every render and loops until React throws *"Maximum update depth exceeded"*. It shipped that way in `ClaimSelect`/`MarketSelect` and crashed the register pages on first load. Return a module-level constant instead (`NO_CLAIMS`, `NO_MARKETS`, and the pre-existing `EMPTY_GRANTS` in `utils/permissions.ts`, which is exactly this pattern done right). The same applies to `.map()`/`.filter()` inside a selector — derive AFTER the hook, not inside it.

**Non-obvious pitfall:** `useDraft` compares its `committed` argument by **value** (JSON), not reference — many callers derive it inline (`.filter()`, `.map()`, `?? []`), which allocates a new array every render even when unchanged; a reference-based comparison resyncs (`setState`) on every render, which is an **infinite update loop** since resyncing triggers a re-render that re-derives yet another new reference (crashed with "Maximum update depth exceeded" the first time this shipped). Fixed via React's "adjust state during render" pattern rather than a `useEffect`.

**Non-obvious pitfall (found 2026-08-26, user-reported "typing lags"): that same value-comparison ran on EVERY keystroke, not just when `committed` actually changed.** `JSON.stringify(committed)` sat unconditionally at the top of `useDraft`'s body — every `patch()` call sets `draft`, which re-renders the component, which re-ran the hook, which re-stringified `committed` (often the WHOLE table's row data) again, synchronously, on the render path of every single character typed into any input using this hook. This is exactly the per-keystroke-cost problem the draft/Save pattern exists to eliminate (see the section intro above) — it had just moved from "stringify + `localStorage.setItem`" to "stringify alone," which is still O(rows × columns) work blocking every keystroke on a large register. Fixed by noting the stringify result is only ever ACTED on when `!dirty` (the resync branch) — wrapping the whole check in `if (!dirty)` skips the computation entirely while an edit is in progress, with no behavior change: `committedJson` just goes stale until dirty clears, and the next `!dirty` render (right after Save or Discard) catches back up. The bigger the register/table, the more this mattered — small tables never showed it.

**Date fields never use the native HTML `<input type="date">` (rule added 2026-08-26, user-requested).** Every date field in the app is antd's `DatePicker` (a text input with a popup calendar), never `<Input type="date">` — the native control renders a browser-chosen (locale/OS-dependent) date box with none of the app's other input styling, which is exactly the inconsistent-small-input complaint the wider 2026-08-26 editable-table UI pass (sticky identity/action columns, dropping `size="small"` app-wide) was already fixing everywhere else. Store the value the same way either control already did — a `'YYYY-MM-DD'` string — converting only at the edges: `value={x ? dayjs(x) : null}` / `onChange={(d) => patch(..., d ? d.format('YYYY-MM-DD') : undefined)}`. Swept and fixed on introduction: `AdminMarketProfiles.tsx`, `AdminRmRisk.tsx`, `GapAssessmentBlock.tsx`, `ChangeDispositionBlock.tsx`, `AssessmentsCard.tsx` (2 fields) were the six native date inputs found across the app; `GateChecksTable`/`GateFlowTable`/`EightAnglesTable` etc. already used `DatePicker`, which is what caught the other six as the outliers.

**Also swept the same day: every shared field-level picker (`UserSelect`, `MarketSelect`, `ClaimSelect`, `NextActionSelect`) had `size="small"` hardcoded INSIDE the component**, so removing `size="small"` at call sites across `DynamicTable`/`SupplierRmEvidenceTable`/`GateFlowTable`/`NextActionsCard`/etc. (part of the same UI pass) had no visible effect on Owner/Verified-by/Market/Claim cells specifically — the picker component itself was still forcing small. Fixed at the source (all 4 components), which is why call-site edits alone are not enough for a shared picker: check the component's own render for a hardcoded `size` before assuming a wrapper prop will override it.

Adding a third label works the same way with no further App.tsx changes; give it an entry in App.tsx's local `submenuIcons` map or it falls back to `<TeamOutlined />`.
